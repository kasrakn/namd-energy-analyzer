# 2JOF Folding — NAMD Parameter Sweep

Molecular dynamics study of the 2JOF (Trp-cage) peptide. Instead of hand-editing
a NAMD config in VMD/NAMDgui for every temperature or step-count you want to
try, `run_namd_sweep.py` takes one template config, patches it for every
combination of temperature / minimization steps / MD steps you ask for, runs
NAMD on each one, and collects the results into a CSV — no VMD required.

## Directory layout

```
.
├── input/              Raw inputs as downloaded/exported, untouched by NAMD
│   ├── 2JOF.pdb                 full PDB entry from RCSB (NMR ensemble)
│   └── rcsb_pdb_2JOF.fasta      sequence
│
├── structure/           Prepared structure actually fed to NAMD
│   ├── 2jof_streight.pdb                straightened starting coordinates
│   ├── 2jof_streight_autopsf.pdb        psfgen/autopsf output: coordinates
│   ├── 2jof_streight_autopsf.psf        psfgen/autopsf output: topology
│   └── 2jof_streight_autopsf_fixed.pdb  autopsf output with fixed atoms flagged
│
├── initial_run/         One-off exploratory run made via the NAMDgui VMD
│   │                     plugin (298 K, minimize 1000, run 10000). Kept as a
│   │                     record and reused as the template for the sweep.
│   ├── 2jof_streight_autopsf.namd       the NAMD config (= sweep template)
│   ├── 2jof_streight_autopsf.log        VMD/NAMDgui log
│   ├── 2jof_streight_autopsf.out        NAMD stdout for this run
│   ├── 2jof_streight_autopsf.{coor,vel,xsc,xst,dcd}   final state & trajectory
│   └── 2jof_streight_autopsf.restart.*  restart checkpoints
│
├── results/              Sweep output, one subdirectory per run (generated)
│   ├── summary.csv                one row per run: final energies, temp, timing
│   ├── summary.json                same data as JSON
│   └── T<temp>_min<N>_md<N>/      per-run config, log, trajectory, restart files
│
├── run_namd_sweep.py     the sweep driver (see below)
├── sweep.json            example sweep definition for --sweep
└── README.md             this file
```

`results/` is fully regenerated by the script — delete it any time and rerun.
Everything under `input/` and `structure/` is static input data; nothing in
this project ever writes into those two directories.

## Requirements

- `namd2` (or `namd3`) on `PATH`. Check with `namd2` — if missing, `module
  load namd` or install it; the script does not bundle NAMD.
- Python 3.9+, standard library only (no pip installs needed).

## Quick start

```bash
# From the repo root:

# 1. See the run matrix and total step count without launching anything
./run_namd_sweep.py -T 300 400 500 -m 1000 -d 50000 --estimate

# 2. Actually run it: 3 temperatures, 2 threads per job, 4 jobs at once
./run_namd_sweep.py -T 300 400 500 -m 1000 -d 50000 -p 2 -j 4

# 3. Look at the results
column -s, -t results/summary.csv | less -S
```

Each run gets its own directory under `results/` named by its parameters
(e.g. `results/T400_min1000_md50000/`), containing the exact `.namd` config
that was run, the full NAMD log (`namd.out`), the trajectory (`.dcd`), final
coordinates/velocities (`.coor`/`.vel`), and a `status.json` with parsed
energies and pass/fail status.

## How it works

`run_namd_sweep.py` never parses the NAMD config into a generic key/value
dictionary (NAMD files have duplicate directives, ordering that matters, and
Tcl variables — a dict loses all of that). Instead it treats
`initial_run/2jof_streight_autopsf.namd` as a **template**: for each
requested combination it makes a copy, surgically rewrites just the lines
that need to change, and leaves everything else — comments, column
alignment, unrelated settings — exactly as it was:

- `coordinates` / `structure` / `parameters` and other input-file directives
  are rewritten to absolute paths, so the copy works from inside its own
  `results/<label>/` subdirectory.
- `set output` (which the NAMDgui template routes every output file through:
  `.dcd`, `.xst`, `outputname`, …) is repointed into that subdirectory.
- `set temperature`, `minimize`, and `run` are overwritten with the requested
  values. A step count of `0` comments the directive out instead of writing
  `minimize 0` (which would just waste a NAMD call).
- Anything passed via `--set KEY=VALUE` is inserted *before* the
  `minimize`/`run`/`reinitvels` lines, because NAMD executes the config
  top-to-bottom as a Tcl script — a setting added after those lines would
  silently never take effect.

It then runs `namd2 +p<threads> <config>` for each generated file (optionally
several at once), parses the resulting log for the `ENERGY:` table, wall-clock
time, and any `FATAL ERROR` lines, and writes one row per run to
`results/summary.csv` / `summary.json`.

## Command-line reference

### Choosing what to sweep

| Flag | Default | Meaning |
|---|---|---|
| `-T`, `--temperatures` | `298` | Temperature(s) in K. |
| `-m`, `--minimize` | `1000` | Minimization step count(s). `0` skips minimization. |
| `-d`, `--md` | `10000` | MD (`run`) step count(s). `0` skips the MD run. |

Each of these accepts, in any mix:
- plain numbers: `-T 300 400 500`
- comma lists: `-T 300,400,500`
- Python-range syntax `start:stop:step` (stop **exclusive**, like `range()`):
  `-T 300:800:100` → 300, 400, 500, 600, 700

`--mode` controls how the three lists combine:
- `product` (default): every combination (cartesian product) — 3 temps × 2
  minimize × 2 md = 12 runs.
- `zip`: pair them up element-wise — `-T 300 400 -m 500 1000 -d 2000 5000`
  makes exactly 2 runs (300/500/2000 and 400/1000/5000), not 8. Shorter lists
  are padded by repeating their last element.

`--sweep sweep.json` reads the sweep from a JSON file instead of `-T/-m/-d`,
either as the same temperatures/minimize/md/mode fields:
```json
{"mode": "product", "temperatures": [300, 350, 400], "minimize": [1000], "md": [10000, 50000]}
```
or as an explicit list of named runs (useful for non-rectangular sweeps):
```json
{"runs": [{"temperature": 300, "minimize": 1000, "md": 50000, "label": "cold"},
          {"temperature": 700, "minimize": 1000, "md": 50000, "label": "hot"}]}
```

`--set KEY=VALUE` overrides or adds any other NAMD directive, repeatable.
Useful for adding a thermostat the template doesn't have, e.g. constant
temperature via Langevin dynamics:
```bash
./run_namd_sweep.py -T 300:800:100 -m 1000 -d 50000 \
  --set langevin=on --set langevinDamping=1 --set 'langevinTemp=$temperature'
```
(Worth knowing: the bundled template has no thermostat, so `run` is
constant-*energy* dynamics — potential energy lost during minimization turns
into kinetic energy, so the system equilibrates noticeably hotter than the
`set temperature` you asked for. Add `langevin` as above if you want the
sweep to actually hold each target temperature.)

### Where things go

| Flag | Default | Meaning |
|---|---|---|
| `--template` | `initial_run/2jof_streight_autopsf.namd` | NAMD config to use as the base. |
| `--outdir` | `results` | Directory to hold one subdirectory per run. Resolved relative to the current directory. |

### Running NAMD

| Flag | Default | Meaning |
|---|---|---|
| `--namd` | `namd2` | NAMD binary to invoke (e.g. `namd3`). |
| `--namd-args` | *(none)* | Extra arguments passed straight to NAMD, e.g. `--namd-args "+setcpuaffinity"`. |
| `-p`, `--threads` | `4` | Threads per NAMD job (becomes `+p<N>`). |
| `-j`, `--jobs` | `1` | How many NAMD jobs to run at the same time. |

Pick `-p` × `-j` to roughly match your CPU count (`nproc`). This machine has
16 cores: `-p 2 -j 4` (8 cores) leaves headroom; `-p 4 -j 4` (16 cores) uses
everything.

### Safety / workflow

| Flag | Default | Meaning |
|---|---|---|
| `--max-runs` | `64` | Refuses to start a sweep larger than this. Range syntax makes it very easy to accidentally request thousands of runs — raise this deliberately if you mean it. |
| `--estimate` | off | Print the run matrix (labels, params, step counts) and exit. Nothing is run. |
| `--dry-run` | off | Write all the generated `.namd` config files but don't launch NAMD. Good for eyeballing the configs before committing CPU time. |
| `--resume` | off | Skip any run whose `results/<label>/status.json` already says `ok` — lets you add more parameter combinations later without rerunning finished ones. |
| `--summarize-only` | off | Don't run anything; just re-read whatever is already in `--outdir` and rebuild `summary.csv`/`summary.json`. Useful after manually deleting/editing a run directory. |

## Reading `results/summary.csv`

One row per run:

| Column | Meaning |
|---|---|
| `label` | Run name, `T<temp>_min<minimize>_md<run>` (or your custom `label` from a `--sweep` JSON). |
| `temperature_K`, `minimize_steps`, `md_steps` | The parameters requested for this run. |
| `status` | `ok` or `failed` (NAMD exited non-zero, didn't reach "End of program", or logged a `FATAL ERROR`/`ERROR:` line — e.g. atoms moving too fast). |
| `returncode` | NAMD's process exit code. |
| `driver_wall_s` / `namd_wallclock_s` / `namd_cputime_s` | Timing: wall clock measured by the driver, and wall/CPU time as NAMD itself reported. |
| `final_ts` | Last timestep NAMD logged an `ENERGY:` line for. |
| `final_total`, `final_potential`, `final_kinetic`, `final_temp`, `final_tempavg` | Energies/temperature from the very last `ENERGY:` line. |
| `potential_initial` | Potential energy before minimization (first `ENERGY:` line). |
| `potential_after_min`, `total_after_min` | Energy right when minimization ends and MD begins — useful sanity check, since this should be identical across runs that only differ in temperature. |
| `n_energy_records` | How many `ENERGY:` lines were logged (sanity check against expected `(minimize + md) / outputEnergies`). |
| `conf`, `log`, `dcd`, `coor` | Paths to that run's config, NAMD log, trajectory, and final coordinates. |
| `error` | First few `FATAL ERROR`/`ERROR:` lines from the log, if any. |

A `failed` row is not necessarily a bug in the script — e.g. skipping
minimization (`-m 0`) on these starting coordinates makes atoms fly apart
(genuine steric clashes in the straightened structure), and NAMD correctly
aborts with "Atoms moving too fast." Always check `error`/`log` before
assuming the sweep itself is broken.
